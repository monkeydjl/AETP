## 1. 总体评价

主文档已具备开展参考 Runtime 验证的结构；是否满足协议保证，仍须以 Conformance、故障注入与真实项目验收为准，不能仅凭文档成熟度判定。以下六个决定我认为在实现阶段价值最大，应当视为不可回退的资产：

1. **十一条冻结区分 + 不变量表（§16）**。实现中每一次争论都可以拿它做仲裁，这是大多数多 Agent 项目缺的东西。
2. **`Command → Event Store → Projection` 从第一天开始（§17.2）**。事件溯源不可以后补，这条底线划得非常对。
3. **Verification 实体化 + evidence 硬性要求（§10.3、INV-017）**。「INCONCLUSIVE 与 FAILED 分开」这类细节说明设计真正想到了运行时。
4. **Transport Adapter 解耦（§2.4）**。v0.1 不被 A2A 绑架，本地先跑通，是正确的工程顺序。
5. **Orchestrator（确定性）与所有平等 Agent（AI）分离（§13.1）**。协调是可选职责，不设 Manager 必经节点。避免了「用一个 LLM 当数据库调度器」的常见错误。
6. **实体表封顶（§4.2）+ v0.1 目标定为 L2**。反 scope creep 的自觉写进了文档本身。

以下建议全部建立在这个前提上：**不是推倒，而是补缝**。

## 2. 协议层补充建议

### S1 🔴 测试的有效性问题：AI 验证 AI 的循环

**问题。** 主文档 §10.3 的 `automated_test` 由 QA Agent 编写并执行。当实现代码与验证代码出自同类模型时，测试可能系统性地偏弱——断言过松、覆盖了 happy path 而漏掉边界、甚至被「说服」通过。协议能保证「存在一条带 evidence 的 Verification 记录」，但**不能保证这条 Verification 有辨别力**。INV-017 防的是伪造，防不了弱测试。

**建议。**

- `verification.method` 增加 `test_authorship` 字段。规则为**默认实现作者 ≠ 测试作者**；低风险 Task（改 README、修 typo、增加纯函数）允许同一 Agent 生成测试以控制成本，但任何情况下**不得由同一 Agent 单独决定 VERIFIED**——「测试作者分离」是默认，「完成判定分离」是不可妥协的底线（第十五轮评审对本条的修正，已并入主文档 §10.3）。
- 支持 `failing_first` 证据：实现提交前存在一条测试 FAILED 的 Verification 记录，证明测试真的能拦住东西（TDD 的协议化表达）。
- 高风险 Task（§9.4）要求 Verification 与 Review 来自**两个不同的 Agent**。
- 引入组织级 **Golden Tests**：由人类拥有、Team 不可修改的验收测试集，任何 Mission 交付前必须通过。这是人类治理在质量层的抓手，而不只是审批层。

**挂靠：** §10.3、§7.3、§16（INV-017）。注：主文档 INV-019 已分配给 Mission Acceptance，本条的「完成判定分离」由 Task 状态机与 INV-017 承载，不再单独立号。

### S2 🔴 集成语义缺失：各自通过 ≠ 合在一起正确

**问题。** §14.8 用 Branch per Agent + Lock 解决了并发写冲突，但有一类问题它管不到：**两个分支各自通过 Review + Verification，合并后语义互相破坏**（例如两个 Task 各自改了 `api.py` 的调用约定，单测都绿，合起来跑不通）。§18.2 当时的 11 类故障注入中「两个 Agent 同时修改同一文件」只测了并发写，没有测合并后语义冲突。目前协议里 Merge 只是 Review 通过后的隐含动作，没有任何状态与记录。

**建议。**

- **Integration Gate**：Task `VERIFIED` ≠ 可合并。合并本身是一条 Command（`git.merge`），产生 `integration.completed` Event，并在集成分支**重跑一次系统级 Verification**，产生新的 Verification 记录——合并不是传播状态，而是一次新的可验证事实。
- 合并冲突显式化：出现冲突时产生 Integration Conflict 记录并路由（回原作者 Agent，或交给集成分支的负责 Role），禁止 Orchestrator 静默 rebase 掉别人的修改。
- 对 §18.2 故障注入清单建议增加第 12 类：**「两个已通过 Review 的分支合并后互相破坏」**（已并入，主文档清单现为 22 类）。

**挂靠：** §10.6、§14.8、§15.1；Integration Gate 已成为主文档规范，上述「缺失」是早期评审背景。

### S3 🔴 执行授权的输入边界：提示注入风险

**问题。** Research / Browser 类 Agent 会读取外部内容（网页、issue、第三方文档）。外部内容可能携带指令，诱导 Agent 发起 Command：创建恶意 Task、提议危险 Decision、外发代码。协议有 Permission 模型管「Agent 能做什么」，但没有「**经过了不可信输入的 Agent 输出需要降权处理**」的概念。§14.3 Credential Broker 隔离了密钥，但没隔离「影响力」。人不在环的 Autonomous 模式下，这是最大的安全缺口。

**建议。**

- 由受信输入入口记录 `external_input_exposure`，并随引用、摘要和跨 Agent 转述传播；Agent 可补充但不能自行清除，来源未知保守标记。执行 / 权威变更请求带 `untrusted_input: true`；普通交流不因此需要逐条审批（第二十轮修订，主文档 §14.11）。
- 带 `untrusted_input` 标记的动作，审批等级自动上调一档（Auto → Agent Review → Human），或要求一个**未暴露于该输入**的 Agent 复核。
- 原则化表述：**外部数据可以成为 Evidence，但不能直接成为 Command 的授权来源。**

**挂靠：** §14.3、§14.4、§9.5（Governance Policy 增加按输入来源分级的规则）。

### S4 🟠 多人治理与审批者缺位

**状态：已并入主文档**（第十八轮）——委托与事后否决、审批角色枚举（多人治理）见 §9.3，Policy 侧的 `delegated` 取值见 §9.5，`EXPIRED` 后续路径由 `on_expire` 定义，暂停期间不计时见 §5.1 Governance Clock。

**问题。** 全文的审批者只有 `human_owner` 一类。两个未覆盖的场景：① 审批人长期不在线，Approval 走到 `EXPIRED` 之后流程如何继续没有定义（是重新发起、升级还是阻塞）；② 个人基础设施长大后天然出现多个人类（所有者 + 协作者），没有委托与分工模型。

**建议。**

- Approval 增加 `delegated_to`，Governance Policy 支持动作级委托（如：指定的合格同行代批 → 人类 7 天内可否决）。这不是 Agent 的上下级审批链，且不可逆 / CRITICAL 动作不使用事后否决替代事前人类审批。
- 规定 `EXPIRED` 的标准后续：产生 Escalation Event，按 Risk Level 重新路由，而不是默认卡死。
- 明确 **PAUSED 期间审批过期计时是否走表**（建议：暂停冻结计时，这需要 Project Clock 区分治理时间与墙钟时间——小改动，但不定清楚实现时必然踩到）。

**挂靠：** §9.3、§5.1（Project Clock）。

### S5 🟠 失败归因：防止信誉污染与模型集中

**问题。** §5.6 的 Performance 与 §6.4 的 Selection Score 挂钩，而失败会被计入成功率。但 Agent 失败的常见原因——API 欠费、限流、网络、Runtime 崩溃——与能力无关。若全部计入，便宜但不稳定的 Provider 会被系统性歧视，最终所有任务集中到最贵最稳的模型上：**信誉机制反过来摧毁了多模型这个立项初衷**。

**建议。**

- Recovery 与 Performance 事件增加 `failure_cause: capability / infra / dependency / external`。
- `infra / dependency / external` 类失败不计入 capability `success_rate`（§10.3 的 INCONCLUSIVE「不计入失败率」已经是同一思想，扩展到 Performance 层）。
- Selection Score 引用的是归因后的能力失败率，而非原始失败率。

**挂靠：** §5.6、§6.4、§11.4。

### S6 🟠 会议成本模型

**问题。** 会议是系统里最贵的行为：8 个参与者 × 3 轮辩论，每轮每人读全部历史发言，token 成本约 O(参与者² × 轮数)。§14.5 Resource Ledger 负责**事后记账**，但没有任何**事前预算控制**。个人基础设施对账单敏感，这一条不解决，「完全托管」跑一个项目可能比人自己写还贵。

**建议。**

- `meeting_policy`（§8.14）增加 `token_budget`，与 `max_rounds` 并列为终止条件之一；预算耗尽强制进入 SYNTHESIS。
- 支持 **Summarize-then-Debate**：第二轮辩论可基于轮换记录者对独立分析轮的摘要，而非重复加载全文；成员仍可查阅原始意见、检查摘要并保留异议——独立轮的完整性由 §8.10 保证，辩论轮的成本由摘要压下来。
- 明确会议**产出与过程分开入库**：Decision / Evidence 入 Event Store，过程发言按 §14.10 ephemeral（已规定，建议在会议一节再强调一次，因为会议是最容易把 Store 撑爆的场景）。

**挂靠：** §8.14、§8.10、§14.5、§14.10。

### S7 🟠 Mission 级验收缺失

**问题。** `mission.completed` Event 存在（§10.4），但 Verification 的 target 只有 artifact（§10.3）。Mission 的 `success_criteria`（§5.2）**谁来验证、怎么验证**没有定义——现在的状态机允许团队自己宣布 Mission 完成，这和「Agent 宣布任务完成」是同一类漏洞，只是抬高了一个层级。

**建议。**

- Mission 进入 COMPLETED 前，要求一轮 **Mission Acceptance**：针对每条 `success_criteria` 生成 Verification（集成测试、部署冒烟、性能基线），并由人类验收作为 CRITICAL 级 Approval（§9.4）。
- Mission 的完成同 Task 一样遵守 INV-004 的精神：**有验收记录才算完成**。

**挂靠：** §5.2、§9.4、§10.3。

### S8 🟡 远程 / 第三方 Agent 的数据出域边界

**问题。** §2.2 的开放性愿景包含第三方 Agent 加入。本地项目的源码、决策、数据集随 Context Package（§12.1）发给远程 Agent 时，没有任何出域控制。密钥有 Credential Broker，**数据没有**。

**建议。**

- Artifact / Context Package 预留数据分级；出域依据是实际模型端点、工具和网络出口，而不是进程是否在本机。完整分级策略可后续实现，但缺少可验证出口限制时不得处理 restricted 数据（主文档 §10.1 / §13.9）。
- 这是 v0.2 接 A2A 之前必须给出答案的问题，v0.1 只需在 schema 预留字段。

**挂靠：** §12.1、§14.3（同一思路从凭证延伸到数据）。

### S9 🟡 Task 的 deadline 与 Lease 分离

**问题。** §7.6 Task Lease 解决活性（Agent 挂了任务不被锁死），但 Mission 有 `deadline` 约束字段（§5.2）而 Task 没有任何调度意义的截止时间。长时间托管时，「每个任务都在正常推进、整体进度已经失控」没有可观测的抓手。

**建议。** Task 增加可选 `due_at`；超期不直接 FAIL，而是触发一次 Replanning 评估（§11.3）——deadline 是进度信号，不是熔断器。

**挂靠：** §7.6、§11.3。

### S10 🟡 Orchestrator 自身的恢复语义

**状态：已并入主文档**（第十八轮）——§13.10 与 INV-021，M0 起生效见 §17.2。

**问题。** 协议详细规定了 Agent 崩溃的恢复（§11.4），但 Orchestrator 本身是单点。v0.1 单进程可接受，缺的只是一句协议规定，避免实现时把 Orchestrator 写成有私有内存状态的服务。

**建议。** 在 §13 或 §17.2 明确：Orchestrator 无自有状态，重启后从 Event Store + State Projection 重建，恢复 Lease / epoch、暂停屏障与 pending Command；先对账 UNKNOWN 外部动作，再恢复允许的调度。Replay 不重新执行历史工具调用。

**挂靠：** §13、§17.2。

## 3. 实现路径建议（与主文档 §18 衔接）

主文档 §18.1（schema 全集）与 §18.2（模拟推演）都是**横向**的。建议实现按**纵向 walking skeleton** 推进——每个里程碑都贯通一条最小事实链，schema 按里程碑增量交付：

| 里程碑 | 内容 | 验收判据 |
| --- | --- | --- |
| M0 | Core Kernel 五对象 + 模拟 Runtime；事务、版本、幂等与纯重放 | 提交后响应丢失仍去重；重启 / 重放得到一致状态，不重做外部动作；不伪造完整 Bootstrap 或 Task 质量验收 |
| M1 | 双 Agent + Message / Artifact / Lease / Checkpoint / Review / Verification + 最小执行边界；仅限固定版本低风险 Policy，需审批的操作暂不放行 | 无 Manager 可直接对话并交付低风险小成果；切换执行后旧 epoch 不能继续写入；无集成面豁免明确留痕 |
| M2 | Discussion / Meeting / Decision / Approval / 风险分级 | 同行讨论真实选型并保留不同意见；无需协调者垄断提案；验证审批快照、执行前拦截与暂停语义 |
| M3 | Team Formation / Blueprint / Task DAG / Integration / Mission Acceptance | 用户只投想法，平等成员讨论方案、按方案协作产生成果并验收；完成正式 Bootstrap，无人工拆任务，通过 TEST-028 |

两条配套原则：

- **每个里程碑同时跑 §18.2 故障注入的对应子集**，注入用例固化为回归测试，而不是一次性推演。
- M0 明确只实现 `Project / Agent / Task / Command / Event` 五个对象，不实现完整 Bootstrap Acceptance。M0–M2 是增量工程里程碑，不能代替 M3 对基本产品设定的完整验收。

## 4. 几点不同意见（取舍提醒）

1. **Consensus Engine / Opinion Weight 建议降级实现。** v0.1 可先用「参与者共同核对、轮换记录者汇总 + minority opinion 永久记录」（§8.15），再由真实项目验证方案质量；汇总者没有最终裁决特权；加权共识引擎（§8.12–8.13）容易产出精确但无意义的置信数字。建议 schema 保留、实现标 v0.2，用 M2 的真实会议检验是否真的需要它。
2. **「假独立」风险。** §8.10 Independent Analysis 的设计意图很好，但要防止实现走样：独立轮必须**物理隔离上下文**（每个 Agent 的 Context Package 单独构造、不含他人输出），而不是在 prompt 里写「请独立思考」。建议把它写成协议要求而非实现建议。
3. **警惕「热闹但不交付」的演示陷阱。** 八个 Agent 聊得热火朝天的 demo 很容易做，但判断系统是否成立的标准只有一条：**Event Store 能否完整回答「这个交付物为什么存在」**（§4.6 事实链）。所有里程碑验收都以可追溯性为准，不以聊天记录的丰富程度为准。
4. **「Autonomy ≠ Unlimited Authority」需要运行时证据。** §9.6 原则正确，但建议在 M2/M3 里真实注入一次「Agent 试图执行 CRITICAL 操作」，验证 Governance Policy 在 Command 与真实工具执行边界均生效（§14.1 / §13.9），不存在原始 Shell / API 旁路，而不是靠 prompt 约束——前者才是协议，后者只是礼貌。

## 5. 协议治理与工程化建议

- **协议变更走 ADR。** 十一条冻结区分每一条都有来历（见主文档附录 A）。建议今后每条区分的修订都以轻量 ADR 记录动机与否决的替代方案，避免 v0.2 时「为什么当初这么定」失忆。
- **Conformance 黄金样例。** §17.4 定义了 Conformance，但没有测试载体。建议 `examples/` 下一份完整的 `autonomous-project.yaml`（合法）+ 每个 schema 配 valid / invalid 成对夹具，让「AETP Compatible」变成可跑的断言而不是自述。

## 7. 结语

主文档明确了「用户投入想法、平等 Agent 讨论方案并产生成果」。本文件关注这些约束能否在真实运行中成立：**S1 测试有效性、S3 输入边界、S2 集成门禁**仍是实现期的重点，但不能靠增加管理层或限制成员对话来替代。

**当前验收口径：** S1–S10 的主要机制已有协议归属；尚待取舍的建议见 §4，第二十轮已采纳要求见 §8。按 M0–M3 逐步实现，使用主文档 §18.2 的 22 类故障注入与 §18.3 的 28 个 Conformance 用例验证；最终以 TEST-028 的完整想法到成果闭环验收，而不是以文档篇幅或聊天热闹程度判定完成。
